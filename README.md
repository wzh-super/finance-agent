# Finance Factor Agent

A standalone, readable implementation of the factor research workflow from
[Microsoft RD-Agent](https://github.com/microsoft/RD-Agent), based on v0.8.0.
An LLM proposes financial factors, writes and repairs Python implementations,
and evaluates them with a fixed LightGBM model and Qlib backtest.

```text
Hypothesis → factor definitions → batch coding and Debug execution
           → Full execution → merge accepted factors and filter duplicates
           → fixed LightGBM / Qlib evaluation → research feedback → next round
```

The project uses an explicit Python loop and JSON checkpoints. It does not import
`rdagent` or require the full RD-Agent installation. Prompts, model responses,
and research reports use English.

## 1. Install the environments

Use **Linux or WSL2, Conda, and Python 3.10**. Native Windows is unsupported because
the runner uses POSIX file locks and process groups. The evaluation model runs on
CPU; a GPU is not required. Full market data and backtests can still require
substantial memory and time.

Run the commands below from this repository's root. Create **two environments**:
the agent environment also executes generated factor scripts; the Qlib environment
exports data and runs training/backtests. Their NumPy constraints differ, so do not
install both requirements files into one environment.

```bash
conda create -n factor-agent python=3.10 pip -y
conda activate factor-agent
python -m pip install -r requirements.txt
python -m pip install --no-deps -e .
python -m pip check

# Requires Git to install the pinned Qlib revision.
conda create -n factor-qlib python=3.10 pip -y
conda activate factor-qlib
python -m pip install -r requirements-qlib.txt
python -m pip check
python -c 'import sys; print(sys.executable)'
```

Save the last command's absolute path for `qlib_python`. On Linux, a missing
`libgomp.so.1` means the system OpenMP runtime is needed (`libgomp1` on Debian/Ubuntu).
You may reuse compatible existing environments instead.

[requirements.txt](requirements.txt) pins the agent's direct dependencies.
[requirements-qlib.txt](requirements-qlib.txt) pins Qlib and key evaluation
dependencies to the existing Linux/Python 3.10 setup. These are not complete
transitive lock files. `pip install -e .` also installs the agent requirements.

## 2. Prepare market data

Market data is not included. The workflow expects:

```text
data/
  qlib/cn_data/          # Qlib daily binary provider
    calendars/day.txt
    instruments/
    features/
  factor_full/
    daily_pv.h5         # Full factor input
    README.md           # Field descriptions supplied to the agent
  factor_debug/
    daily_pv.h5         # Small coding/debugging sample
    README.md
```

Reuse existing inputs if available, keeping all three datasets on the same data
version and adjustment convention. Paths may point outside the repository.
Otherwise, download a Qlib provider and export the factor inputs:

```bash
conda activate factor-qlib
python -m qlib.run.get_data qlib_data \
  --target_dir ./data/qlib/cn_data --region cn --interval 1d --delete_old False
python tools/prepare_data.py --provider ./data/qlib/cn_data --output ./data
```

Download availability depends on the upstream data source. The export script reads
existing data without API calls or training and refuses to overwrite its output
directories. Full data starts on `2008-12-29`; Debug covers 2018–2019 for up to the
first 100 instruments in Full data. Missing observations are preserved.

Each HDF file uses key `data`, a `(datetime, instrument)` index, and columns
`$open`, `$close`, `$high`, `$low`, `$volume`, `$factor`. Here `$factor` is the price
adjustment factor, not a predictive factor generated by the agent.

The supplied evaluation templates use CSI300 and benchmark SH000300, with training
in 2008–2014, validation in 2015–2016, and testing from 2017 to `2020-08-01`.
The provider must contain the required history, instruments, and benchmark.
The Full factor input can cover a broader universe than the backtest.

## 3. Configure paths and API access

```bash
cp config.example.yaml config.yaml
cp .env.example .env
chmod 600 .env
```

Edit `config.yaml`, replacing the interpreter path with the one printed above:

```yaml
data_dir: ./data/factor_full
debug_data_dir: ./data/factor_debug
qlib_provider: ./data/qlib/cn_data
qlib_python: /absolute/path/to/envs/factor-qlib/bin/python
```

Relative data paths resolve against the YAML file's directory. Factor scripts use
the agent's Python interpreter by default, so activate `factor-agent` before running.

Set the following in `.env`:

| Variable | Purpose |
| --- | --- |
| `OPENAI_API_KEY` | Your provider's API key; keep it local |
| `CHAT_MODEL` | Model ID for hypotheses, code, reviews, and research feedback |
| `EMBEDDING_MODEL` | Model ID for coding-memory similarity retrieval |
| `OPENAI_API_BASE` | Optional OpenAI-compatible endpoint, including its API path |

Chat and embeddings share the endpoint and key. The chat endpoint must support
Chat Completions, JSON object output, and `temperature`. The client removes an
initial `openai/` model prefix and does not switch providers or models on failure.
Existing shell variables take precedence over `.env`.

Keep the example files unchanged for publication. The program does not load
`.env.example` or `config.example.yaml` automatically: copy them as shown above,
then replace every placeholder in the local copies. The example data directories
are not bundled; set them to your actual datasets, using absolute paths if needed.

Keep `.env` and `config.yaml` in the project root, alongside `run.py`, and run
all commands from that directory. The program reads `.env` there by default;
select the YAML file with `--config config.yaml`. Neither local file should be
committed.

Defaults propose 1–5 factors per research round, allow up to 10 **shared batch
coding rounds**, and use 3,600-second factor/backtest timeouts. Override settings
such as `max_coding_attempts`, `factor_timeout`, or `backtest_timeout` in YAML only
when needed. See [config.py](factor_agent/config.py) for all fields.

## 4. Check and run

```bash
conda activate factor-agent
python run.py check --config config.yaml --env-file .env
python -m unittest discover -s tests -v
```

`check` checks input paths and interpreters and reports package versions; it does
not call an API, train a model, or establish data completeness/API availability.
The tests use synthetic inputs and API/backtest substitutes, with small local
factor subprocesses. They need neither market data nor credentials nor a Qlib
environment.

Start a live research run:

```bash
python -u run.py run --config config.yaml --env-file .env \
  --run-dir runs/research_01 --rounds 1
```

This calls the configured chat/embedding APIs, incurs provider charges, and runs
factor computation, LightGBM training, and Qlib backtests. Each run needs its own
directory; concurrent writers to the same directory are rejected.

Resume until **five total rounds** have completed:

```bash
python -u run.py resume --config config.yaml --env-file .env \
  --run-dir runs/research_01 --rounds 5
```

`--rounds` includes already completed rounds. Interruptions preserve completed
stages, but unfinished computation/training may restart. Source, configuration,
data, and dependency fingerprints prevent resuming with incompatible inputs.
Use a new run directory after changing these inputs. Saved paths are absolute;
moving a run directory is not a supported way to resume it elsewhere.

Read or regenerate a saved trajectory without API calls or computation:

```bash
python run.py show --run-dir runs/research_01
python run.py show --run-dir runs/research_01 \
  --output runs/research_01/trajectory.md
```

## Project structure

```text
run.py                        CLI entry point
factor_agent/
  pipeline.py                 Explicit research loop; start reading here
  models.py                   Factor, attempt, feedback, and state data objects
  research.py                 Hypotheses, factor design, and research feedback
  coding.py                   Batch code generation, review, and repair
  memory.py                   Successful code, failures, and similarity retrieval
  execution.py                Factor subprocesses, timeouts, validation, and cache
  backtest.py                 Full execution, factor merging, correlation filtering
  qlib_worker.py              Training/backtesting in the Qlib environment
  llm.py                      API requests, response cache, and scripted replay
  storage.py                  JSON checkpoints and reports
  trajectory.py               Source snapshots and readable artifact views
  progress.py                 Terminal progress and event logging
  config.py / cli.py          Configuration and component assembly
  prompts/                    Research and coding prompt assets
  templates/                  Fixed LightGBM/Qlib evaluation settings
tools/prepare_data.py         Export Qlib data to Full/Debug HDF inputs
tests/                       Offline regression tests
requirements*.txt            Dependencies for the two environments
config.example.yaml          Portable path configuration example
.env.example                 API configuration placeholders
```

Runs preserve `state.json`, raw requests/responses in `llm/`, coding memory,
`source_snapshot/`, every attempt under `rounds/`, baseline results, and progress
logs. `report.md` and `trajectory.md` are readable views of these artifacts.
Implementation success, participation in a backtest, and research acceptance are
separate decisions. Only new factors actually evaluated and accepted by research
feedback enter the accepted-factor library; coding memory can retain correct
implementations even when returns do not improve.

## Development and evaluation scope

Edit `research.py` / `pipeline.py` for research policy, `coding.py` / `memory.py`
for code evolution, and `prompts/` for instructions. Run the relevant offline tests
before starting a new experiment. Generated factor code runs in local subprocesses;
timeouts and credential filtering do not provide an operating-system sandbox.

Core research behavior is retained, while framework abstractions, environment
management, and knowledge retrieval are simplified. Exact upstream trajectories
are not reproduced. Baseline and combined-factor templates retain different
preprocessing, and test-period results are fed back into research. Iterative
returns therefore are not independent held-out evidence of factor quality.

Commit source, tests, configuration examples, and this README. `.gitignore` excludes
credentials, local configuration, data, run artifacts, and build caches. Preserve
original trajectories and failed attempts in experiment storage outside the public
source repository. Ignoring a file does not remove it from Git if already tracked.
